Como os componentes do Neon fazem commit com durabilidade e recuperam páginas PostgreSQL, sem exigir acesso síncrono ao S3 em cada operação.

Pipeline de persistência

Transação PostgreSQL → WAL quorum → pageserver → storage

⚠

Precisão importante: no Neon, o commit espera um quorum de Safekeepers duráveis. O pageserver processa WAL e envia layers posteriormente ao armazenamento de objetos. Já TiKV, CockroachDB e ScyllaDB utilizam armazenamento ativo persistente em seus nós; S3 não é o write path primário desses sistemas.

03 / NEON DATABASE

Cada tenant pode ter seu próprio PostgreSQL?

Sim, se você provisionar um compute endpoint por branch ou projeto. Mas PostgreSQL independente, armazenamento segregado e isolamento físico são três conceitos distintos.

ISOLAMENTO POR CAMADA
⌘

Compute independente

Um endpoint PostgreSQL primário por branch pode ter CPU/RAM e ciclo de vida próprios. Cada branch tem um escritor primário.

▤

S3 lógico por tenant

O storage identifica tenants, timelines e objetos por caminhos/chaves lógicos. Não exige bucket ou pasta física exclusiva por cliente.

⇄

Infra compartilhada

Safekeepers, pageservers e control plane podem servir múltiplos tenants. Isso reduz custo, mas exige limites e controle de ruído.

Modelo econômico

Bancos no mesmo compute

Múltiplos databases/schemas no mesmo PostgreSQL primário. Barato, mas compartilham write throughput, recursos e falhas do mesmo processo.

Modelo recomendado para isolamento

Branch/compute por tenant

Writer independente por tenant. O agregado de gravação cresce com novos computes, limitado pelo storage, quorum, quotas e cluster subjacente.

Modelo enterprise

Projeto/cluster dedicado

Recursos e políticas com separação mais forte. Maior custo e operação; útil para tenants críticos ou requisitos regulatórios.

06 / DECISÃO

Qual tecnologia para cada workload?

Seleção orientativa por padrão de acesso e exigências de consistência. Testes reais com seus dados continuam obrigatórios.

🏢

SaaS B2B multi-tenant

Neon com endpoint PostgreSQL por tenant/branch, limites de recursos, suspensão dos ociosos e pooling de conexões. Adequado a workloads SQL variáveis.

NEON · PG · OBJECT STORAGE
⚡

Ingestão de alta taxa

ScyllaDB para acesso key-value bem particionado; TiDB para SQL distribuído com sharding físico. O p99 e a distribuição das keys determinam a eficiência.

SCYLLADB · TIDB · K8S
🛡️

ACID e operação multi-região

CockroachDB ou Spanner quando transações distribuídas e resiliência geográfica compensam latência de consenso e custo de operação.

COCKROACHDB · SPANNER
